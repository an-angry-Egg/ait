# AIT Demo 开发方案

## 1. 验证什么

一条链路：**画圈 → 说一句 → 命中目标与源码位置 → 浮窗成稿 → 提交上下文包 → 看到改动生效。**

验证的是交互是否成立，不是语音识别精度，也不是真改源码。

## 2. 形态：真 Chrome 扩展 + 自带演示页

不使用静态 HTML 模拟。理由：画圈命中、`elementFromPoint` 命中顺序、shadow DOM 穿透、页面点击被拦截——这四件事只有真实注入才能验证，静态页模拟出来的全是假的，验证不到任何东西。

```
demo/
├── index.html          演示业务页（带 data-ait 与假后端日志）
├── assets/app.css      页面样式
├── assets/app.js       页面自身逻辑（登录、表格、埋日志）
└── extension/          未打包扩展，chrome://extensions 加载
    ├── manifest.json
    └── content.js      全部逻辑（画圈 / 命中 / 浮窗 / 匹配 / 草稿 / 提交）
```

## 3. 不做的部分

| 不做 | 原因 | 归属 |
|---|---|---|
| sherpa-onnx 本地语音 | 模型 100MB+，需 VAD/KWS 调参 | M3 |
| 真读源码、`tsc`、git 快照 | 需本地桥 | M2 / M5 |
| 真调 LLM | Demo 不持密钥 | — |
| 真 MCP / ACP 投递 | 用剪贴板 + 上下文面板替代 | M5 |

`data-ait` 属性直接在演示页里手写，模拟编译期注入的结果——证书链正确，只差产物来源。

## 4. 输入层：双通道

**默认通道：模拟语音条。** 打字回车 = 说完一句，走与真实语音完全相同的管线（清洗 → 入草稿 → 匹配）。这不是偷懒：M3 要换的只有"文本从哪来"这一层，其余管线不变。

**可选通道：Web Speech API。** 点麦克风按钮真说话，`SpeechRecognition` 可用则接管，不可用（未联网、非 Chrome、被策略禁用）自动回落并提示原因。**不做静默降级。**

不接 sherpa-onnx 的原因写在这里，免得被当成遗漏：它属于 M3，且 Demo 要证明的是交互，不是识别率。

## 5. 画圈的三个实现要点

**① 触发不靠键盘。** 待机时浮窗只有一个圆形「点睛」按钮，点击进入聆听态——这个按钮就是唤醒词的占位，M3 换成语音唤醒后删除。

**② 聆听态下左键拖动即画圈，页面点击被完全拦截。** 在 `document` 的捕获阶段接管 `mousedown` / `mousemove` / `mouseup`，全程 `preventDefault` + `stopPropagation`，**不产生任何 `click`**。这是"指向无副作用"的实现层保证。

**③ 命中靠采样，不靠包围盒。** 沿圈的包围盒打 8×8 网格，每点调 `elementsFromPoint`，取最上层可选元素计票；过滤 `html`/`body`/浮窗宿主/零尺寸节点；按"票数降序 + 面积升序"排序，取前 5 为候选。包围盒判定会把整块容器选进来，采样判定能自然贴合形状。

## 6. 语义匹配打分

候选与口述文本逐项计分，取最高者为锁定目标，其余作为备选留在浮窗：

| 条件 | 分值 |
|---|---|
| 命中元素可见文本（完整包含） | 60 |
| 命中 `aria-label` / `placeholder` / `title` | 45 |
| 指令中的名词命中标签语义（按钮/输入/表格/卡片…） | 20 |
| 采样票数 | ≤15 |
| 有 `data-ait`（源码可定位） | 5 |
| 面积越小越精确 | ≤10 |

分数显示在浮窗上，便于判断"它认错没有"。阈值以下不进候选，全部低于阈值时按票数直接取第一。

## 7. 浮窗

按产品定稿 §5.3 实现：320px、右上角 16px、13px/1.5、深色毛玻璃、单一蓝色强调色、shadow DOM + `pointer-events: none`。

`pointer-events: none` 与"浮窗上有输入框"冲突，处理方式：**宿主 `none`，只有输入条与按钮 `auto`**。这样鼠标能透过浮窗点中页面，同时浮窗自己的控件可用。

四态：待机（只有圆钮）/ 聆听 / 草稿 / 执行完成。文案直接取 §5.4 的表。

## 8. 提交与"改动生效"

「开始改」后依次做四件事，全部在前端：

1. 组装上下文包（`taskId`、`page`、`target`（含 `data-ait` 源码位置）、`instruction.raw`、`draft[]` 按句数组、`traces[]`、`logs[]`），在浮窗内可展开查看
2. 同时写入剪贴板，作为"投递给真 Agent"的降级路径
3. 按指令关键词真的改目标元素样式（绿色→背景色、大一点→字号、加粗、隐藏…），模拟 HMR 生效
4. 显示"已改好 · n 处变更 · 撤回？"，撤回恢复内联样式

这一步的意义：**不改样式，Demo 就只是又一个聊天框。** 改动必须可见，用户才能判断"它理解对了没有"。

## 9. 假日志的意义

演示页在按钮点击、表单提交时向 `window.__AIT_LOGS__` 追加结构化日志（`trace_id` / `method` / `path` / `status` / `message`）。画圈命中后，扩展按 `trace_id` 捞取并显示在浮窗与上下文包里。

这是把"日志关联"这个差异化点在 Demo 里变成可见的东西——否则它只是一句设计主张。

## 10. 验收

| 项 | 标准 |
|---|---|
| 画圈不触发页面行为 | 圈过按钮后，页面无跳转、无请求、无弹窗 |
| 命中准确 | 圈住「编辑资料」按钮，锁定的就是它 |
| 源码位置 | 浮窗显示 `ProfileCard.vue:45` |
| 语义匹配 | 圈内 3 个按钮，说"编辑"，锁定编辑按钮 |
| 草稿可用 | 累积多句、删指定句、改错能修 |
| 上下文包 | JSON 字段完整，`draft` 为句数组，`logs` 带 `trace_id` |
| 改动可见 | 说"改成绿色"后按钮真变绿，撤回恢复 |
| 穿透 | 浮窗遮挡处能点中下面的页面元素 |

## 11. 开发顺序

1. 演示页（含 `data-ait`、假日志）
2. 扩展骨架 + 浮窗四态（假数据）
3. 画圈与命中测试
4. 语义匹配 + 草稿编辑
5. 上下文包 + 改样式 + 撤回
6. Web Speech 可选通道

## 12. 运行

```powershell
cd D:\code\MidasUI\demo
.\start.ps1
```

脚本会起静态服务（5199）并打开浏览器。等价的手动方式：

```powershell
python -m http.server 5199
```

1. 打开 `http://127.0.0.1:5199/`
2. `chrome://extensions` → 开发者模式 → 加载已解压的扩展程序 → 选 `demo\extension`
3. 刷新页面 → 点右上角「点睛」→ 在页面上拖一个圈 → 输入条打字回车 → 点「开始改」

注意：Chrome 137 起正式版禁止了 `--load-extension`，扩展只能手动加载，脚本无法代劳。

## 13. 已验证

本机实测（CDP 驱动无头 Chrome，将 `content.js` 注入页面执行）：

| 项 | 结果 |
|---|---|
| 浮窗挂载与四态切换 | ✓ 待机→聆听→草稿→完成 |
| 画圈命中 | ✓ 圈住「编辑资料」锁定「编辑资料」，标签 `ProfileCard.vue:45` |
| 语义匹配 | ✓ 3 个候选中说「编辑」锁定编辑按钮 |
| 画圈无副作用 | ✓ 全程无 `click`、无跳转、无表单提交 |
| 草稿编辑 | ✓ 两句累积、`第二条不要` 删对、`×` 单独删除 |
| 上下文包 | ✓ 字段完整，`draft` 为句数组，`logs` 带 `trace_id` |
| 改动可见 | ✓ 背景 `rgb(16,185,129)`，撤回恢复 `rgb(37,99,235)` |

**一处必须说明的差异**：上述验证是把 `content.js` 注入页面主世界执行的，真实扩展运行在隔离世界。两者的 DOM 行为一致，但**扩展的注入本身（manifest、权限、matches）只能在浏览器里手动加载后才算验证过**。`runtime.chrome` 相关 API 在 Demo 中未使用，因此注入方式的差异不影响逻辑正确性。
